# Lecture 9: Introduction to Process

1. What is a program? Compiled code, that is ready to execute.
   - You write code in a text file (e.g. `.cpp`); the compiler converts it to machine code and produces an executable. That executable is the program.
   - The source text file is not ready to execute; the executable is.
   - A program resides on disk (e.g. a game sitting on disk until you double-click it).
2. What is a process? Program under execution.
   - When a program is run, the OS converts the program into a process.
   - A process is a unit of work done by a computer.
   - Why a process? It is the way a user gets work done by the computer: user writes code, compiler turns it into a program, OS turns the program into a process and executes it, and the program's intended work happens.
3. How OS creates a process? Converting program into a process.
   **STEPS**:
   a. Load the program & static data into memory.
      - Memory here = RAM (main memory). The program's instructions and data are copied from disk into memory.
      - Static data = data used for initialisation, written in the program itself (not dynamically allocated).
      - Example: `char *name = "Lakshay";` the string is static data. When the process creates the variable `name`, the OS must know what to initialise it with, so it copies this data and assigns it.
      - Example: `int a = 0;` the value `0` used to initialise `a` is static data.
   b. Allocate runtime stack.
      - Stack: part of memory used for local variables, function arguments and return values.
      - Needed for function calls and recursion: when a function calls another, the caller's data is saved on the stack and control jumps to the called function.
   c. Heap memory allocation.
      - Heap: part of memory for dynamic allocation.
      - Data declared while writing code (`int a`, `int b`) is already there; at runtime the program may need more memory for a while, which it asks for from the heap via `malloc` / `new`.
   d. IO tasks.
      - In Unix, after the above steps, three IO descriptors (handles) are created for the process: one for input, one for output, one for errors.
      - Input handle: where the process reads input from.
      - Output handle: where the program's output is written.
      - Error handle: where errors generated by the program go.
      - Example: `fprintf(stderr, "...")`. The first argument of `fprintf` can be a file descriptor (to write into a file) or an error handle. `stderr` is the standard error handle; it prints the error on the console.
   e. OS handoffs control to main ().
      - The OS has allocated sufficient stack, heap and handled IO; now the program's instructions start executing.
      - Execution always starts from `main()` because the OS only knows `main`, not any other function.
      - Once the OS calls `main`, it steps back: the process now controls the CPU and the memory the OS allocated to it. The OS's job of creating the process is done.
      - `return 0` at the end of `main`: every process is created as a child of some parent process (here, think of the parent as the OS). When the child finishes, the parent must know whether execution was successful, so the programmer can e.g. show an error otherwise.
        - `return 0` (or `exit(0)`) tells the OS the program executed successfully.
        - If the program exits earlier with, e.g., `exit(-1)`, the OS sees that it did not return/exit 0, i.e. something went wrong. The program handles that error its own way.
4. **Architecture** of process:

   The process as it sits logically in memory:

   ```
   ┌───────────────────┐
   │       Stack       │  Local variables, function arguments & return values
   │         │         │
   │         ▼         │  (stack grows down)
   │                   │
   │         ▲         │  (heap grows up)
   │         │         │
   │       Heap        │  Dynamically allocated variables
   ├───────────────────┤
   │       Data        │  Global & Static data
   ├───────────────────┤
   │       Text        │  Compiled code (Loaded from disk)
   └───────────────────┘
   ```

   - Text: the compiled code loaded from disk. An executable is still a file; open one in Notepad and you see strange characters because Notepad cannot read machine code.
   - Data: global variables (global to a file, or to the whole program, e.g. with external linkage so a variable is accessible from one module in another) and static data.
   - Heap and stack: at the start of execution the OS keeps the stack and heap far apart, so each has sufficient space for the program to execute.
   - **Stack overflow**:
     - Each recursive call stores the current call's variables on the stack and allocates another stack area for the next call with its arguments.
     - With no base case (exit condition), calls keep piling up and the stack keeps growing.
     - After a certain limit, when the stack grows until it meets the heap, the OS throws a stack overflow error before the whole memory gets corrupted.
   - **Out of memory error** (or memory insufficient error, depending on the system):
     - RAM is limited, and each process gets only a certain limit, since the OS has many other processes.
     - Languages like Java have a garbage collector, so you need not free memory. C++ demands discipline: if you allocate on the heap, freeing it is your responsibility.
     - If a developer keeps allocating on the heap (e.g. 100 MB at a time) and never frees it, at some point the heap touches the stack and an out of memory error is thrown.
   - Both errors are "memory ran out" errors. How to avoid them:
     - Stack overflow: in recursive calls, set a base case so recursion stops at some point, returns, and unwinds the stack.
     - Stack unwinding: each recursive call adds a level on the stack; when the base condition hits, the calls return one by one and the stack is freed back. Without unwinding, stack overflow occurs.
     - Out of memory: deallocate unnecessary objects you allocated on the heap.
5. **Attributes** of process:
   a. Feature that allows identifying a process uniquely.
      - Many processes are loaded at once (P1, P2, ...); the OS treats each separately, and attributes are how it differentiates them.
   b. Process table
      i. All processes are being tracked by OS using a table like data structure.
      ii. Each entry in that table is process control block (PCB).
      - The OS is a manager: it writes down all processes (P1, P2, P4, ...) in the process table, so it knows which processes it currently has.
   c. PCB: Stores info/attributes of a process.
      i. Data structure used for each process, that stores information of a process such as process id, program counter, process state, priority etc.
      - Every process has its own PCB. The OS identifies a process only through its PCB, so logically the PCB is the process.
      - Context switching (previous lecture) saves a process's data temporarily in its PCB.
6. **PCB structure**:

   | Field | Description |
   |---|---|
   | Process ID | Unique identifier |
   | Program Counter (PC) | Next instruction address of the program |
   | Process State | Stores process state |
   | Priority | Based on priority a process gets CPU time |
   | Registers | |
   | List of open files | |
   | List of open devices | |

   - The exact data structure used for the PCB does not matter; visualise it as blocks holding 7 types of information.
   - **Process ID**: unique identification. The OS runs a counter from 0 since boot; each new process gets the next number (e.g. 23, then 24).
   - **Program Counter**:
     - After compiling, a program becomes a collection of CPU instructions (e.g. an `ADD` instruction), at positions 0, 1, 2, ...
     - The CPU is "dumb": it just executes instructions in sequence as they are given.
     - The OS associates a program counter with each process, initialised to 0 (the first instruction is at position 0).
     - PC stores the address of the instruction to run, like a pointer; it keeps track of where the process is. Without it, the CPU would not know the next instruction.
     - Flow:

       ```mermaid
       flowchart LR
           A["Fetch instruction from address in PC"] --> B["PC++"]
           B --> C["Execute instruction"]
           C --> A
       ```

     - CPU checks the PC (say 1), fetches and decodes the instruction at address 1, increments PC (now 2), executes the instruction, then moves to address 2, and so on till the program terminates.
   - **Process State**: which state the process is currently in: new, wait, run (got the CPU, executing), etc. (States covered in the next lecture.)
   - **Priority**: a high priority job must be executed first. Its priority is written in its PCB, and that decides how the CPU scheduler treats it.
   - **Registers**: the CPU has many registers, e.g. SP (stack pointer, points to the stack), BP (base pointer), CR (control registers). When a running process P1's time ends (it must go to wait state for an IO operation, or its time quantum expires), the values in the CPU registers are saved as-is into the PCB's registers block during the context switch. When P1 is scheduled again, they are restored into the CPU registers.
   - **List of open files**: file descriptors (FDs) of files the process has opened to read or write.
   - **List of open devices**: device descriptors of devices (IO) the process has opened, e.g. to read from.
   - Whenever the OS needs any information about a process, it finds it in that process's PCB.

**Registers in the PCB**, it is a data structure. When a processes is running and it's time slice expires, the current value of process specific registers would be stored in the PCB and the process would be swapped out. When the process is scheduled to be run, the register values is read from the PCB and written to the CPU registers. This is the main purpose of the registers in the PCB.
