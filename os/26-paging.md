# Lecture 26: Paging | Non-Contiguous Memory Allocation

1. The main **disadvantage of Dynamic partitioning is External Fragmentation.**
   1. Can be removed by Compaction, but with overhead.
      - Compaction (defragmentation) has to be done again and again as processes come and go, so the overhead keeps adding up.
   2. **We need more dynamic/flexible/optimal mechanism, to load processes in the partitions.**
   - Recap example: RAM = OS 4KB, P1 2KB, P3 1KB, P2 2KB. P1 and P2 exit, so the free list has two separate 2KB holes (2KB -> 2KB -> NULL). A new process P4 of 3KB arrives. 4KB is free in total, but no single hole is 3KB, so contiguous allocation fails.

2. **Idea behind Paging**
   1. If we have only two small non-contiguous free holes in the memory, say 1KB each.
   2. If OS wants to allocate RAM to a process of 2KB, in contiguous allocation, it is not possible, as we must have contiguous memory space available of 2KB. (External Fragmentation)
   3. **What if we divide the process into 1KB-1KB blocks?**
      - Then some part of the process goes into one hole and the rest into the other hole. This is non-contiguous allocation, and paging is such a method.

3. Paging
   1. **Paging is a memory-management scheme that permits the physical address space of a process to be non-contiguous.**
   2. It avoids external fragmentation and the need of compaction.
   3. Idea is to divide the physical memory into fixed-sized blocks called **Frames**, along with divide logical memory into blocks of same size called **Pages**. (# Page size = Frame size)
      - The process is its logical address space. Each fixed-size piece of the logical address space is a **page** (page 0, page 1, page 2, ...).
      - Each fixed-size piece of the actual RAM (physical memory) is a **frame**. Page and frame are only two names: page = fixed partition of a process's logical (virtual, imaginary) address space, frame = fixed partition of real RAM.
      - Example: process of 64KB, page size 16KB, so 4 pages (page 0 to page 3). RAM of 128KB is divided into 16KB frames, so 8 frames; assume the first frame holds the OS.
      - Some frames are already occupied by other processes and the free frames are scattered. With contiguous allocation (dynamic partitioning) the 64KB process cannot be loaded, because no 64KB contiguous hole exists; we would have to defragment first.
      - With paging, each page is picked up and put into any free frame, even if the frames are far apart (e.g. page 3 in one free frame, page 2 in another, and so on). RAM no longer needs contiguous free space; it only needs enough free frames.
      - A page needs exactly one frame because page size = frame size (a 16KB page needs a 16KB slot, just like a 64KB contiguous process needed 64KB).
      - RAM is bigger than a process, so RAM has more frames than the process has pages, but every frame is still the same size as a page.
   4. **Page size** is usually determined by the processor architecture. Traditionally, pages in a system had uniform size, such as 4,096 bytes. However, processor designs often allow two or more, sometimes simultaneous, page sizes due to its benefits.
      - Page size is decided by the processor/system architecture (a computer architecture topic, not covered here). For now assume page size is fixed. Traditional systems used 4KB.
      - So paging = dividing the logical address space into pages and the physical address space into frames of the same size, and placing pages in any free frames.
   5. **Page Table**
      1. A Data structure stores which page is mapped to which frame.
      2. **The page table contains the base address of each page in the physical memory.**
      - In contiguous allocation, the MMU translated a logical address by adding it (offset) to the base stored in the relocation register, checked against the limit register. In paging, the MMU uses a table data structure, the page table, to convert logical addresses to physical addresses.
      - Example page table for a 4-page process: page 0 -> frame 3, page 1 -> frame 7, page 2 -> frame 5, page 3 -> frame 2.
      - **Each process has its own page table**, because each process has its own logical address space and its pages are mapped to different frames (another process P1 may have 3 pages placed in some other frames, so its table is different).
      - In real memory the page table has no "page number" column. It is a simple array indexed from 0 to n, holding frame numbers; the page number is used as the index, like `a[0]`, `a[1]`.
   6. Every address generated by CPU (logical address) is divided into two parts: a page number (p) and a page offset (d). The p is used as an index into a page table to get base address the corresponding frame in physical memory.
      - Worked example (address translation with bits):
        - Logical address space of process P0 = 64 bytes, page size = frame size = 16 bytes, so 4 pages. Logical address needs 6 bits (2^6 = 64): the left 2 bits are the page number p (2^2 = 4 pages), the right 4 bits are the offset d (2^4 = 16 bytes per page).
        - Physical memory = 128 bytes = 8 frames of 16 bytes. Physical address needs 7 bits: 3 bits frame number f (2^3 = 8 frames) + the same 4 bits offset d.
        - Page table: page 0 -> frame 3, page 1 -> frame 7, page 2 -> frame 5, page 3 -> frame 2.
        - Logical address 25 = `01 1001`. p = `01` = page 1 (page 1 starts at 16), d = `1001` = 9. Check: base 16 + offset 9 = 25.
        - Page table entry for page 1 gives frame 7 = `111`. Frame 7 starts at 7 × 16 = 112.
        - Physical address = `111 1001` = 112 + 9 = 121.
        - The offset d is copied unchanged, because the whole page is moved as it is into the frame: the page's base 16 maps to the frame's base 112, so any offset (here 9) lands at the same offset in the frame. Only p is replaced by f, using the page table.

      | Logical address 25 | p = `01` (page 1) | d = `1001` (9) |
      |---|---|---|
      | **Physical address 121** | **f = `111` (frame 7)** | **d = `1001` (9)** |

      **Paging model of logical and physical memory**

      | Logical Memory Process P1 | Page Table (page -> frame) | Physical Memory (frame: content) |
      |---|---|---|
      | Page 0 | 0 -> 1 | 0: |
      | Page 1 | 1 -> 4 | 1: Page 0 |
      | Page 2 | 2 -> 3 | 2: |
      | Page 3 | 3 -> 7 | 3: Page 2 |
      | | | 4: Page 1 |
      | | | 5: |
      | | | 6: |
      | | | 7: Page 3 |

      - Process 1 is divided into 4 pages (index 0 to 3): page 0 goes to frame 1, page 1 to frame 4, page 2 to frame 3, page 3 to frame 7.
   7. Page table is stored in main memory at the time of process creation and its base address is stored in process control block (**PCB**).
      - Every process has its own PCB (holding register values, program counter, etc.), kept by the OS in the kernel area of RAM. Each process's PCB stores the location (base address) of that process's page table in memory.
   8. A page table base register (**PTBR**) is present in the system that points to the current page table. Changing page tables requires only this one register, at the time of context-switching.
      - Current page table = page table of the process that is scheduled (running) now.
      - Example: P1 is running, so PTBR holds the address of P1's page table. P1 goes for I/O and P2 gets the CPU. On this context switch, the OS reads the page table address from P2's PCB and loads it into PTBR, replacing P1's value.
      - So the only extra work paging adds to context switching is changing this one register.

4. **How Paging avoids external fragmentation?**
   1. Non-contiguous allocation of the pages of the process is allowed in the random free frames of the physical memory.
      - In the example, frames 1, 4 and 6 were busy, yet the 64KB process was loaded by putting its pages in whichever frames were free. So paging has no external fragmentation.

5. **Why paging is slow and how do we make it fast?**
   1. There are too many memory references to access the desired location in physical memory.
      - The page table itself is stored in RAM (in the OS area). To reach physical location 121 for logical address 25: reference 1 goes to the page table in RAM to get the frame number, reference 2 goes to the actual location in RAM. One extra memory reference per access, only because of the table.
      - Also, processes context switch all the time, and each new process's page table also comes from RAM.
      - Paging itself is a costly process, so making it fast is necessary. Idea: use caching.

6. **Translation Look-aside buffer (TLB)**
   1. A Hardware support to speed-up paging process.
      - It is hardware support, not software support. The TLB is itself a piece of hardware holding a table; it is not a table stored in memory like the page table.
   2. It's a hardware cache, high speed memory.
      - TLB access time is less than memory (RAM) access time. Cost-wise, TLB hardware is also more expensive than RAM.
   3. TLB has key and value.
      - Key = page number, value = frame number (key-value pairs).
   4. Page table is stored in main memory & because of this when the memory references is made the translation is slow.
   5. When we are retrieving physical address using page table, after getting frame address corresponding to the page number, we put an entry of the into the TLB. So that next time, we can get the values from TLB directly without referencing actual page table. Hence, make paging process faster.
      - Without TLB: CPU generates logical address (p, d). p indexes the page table in memory to get f. (f, d) is the physical address.
      - With TLB: the CPU first checks the TLB for p.
        - First access to page `01` (e.g. address `01 1001`): not in TLB (miss), so it is resolved through the page table, frame `111` is used, and the entry (`01` -> `111`) is also put into the TLB.
        - Next access to any address starting with `01` (e.g. `01 0111`): the CPU does not go to the page table; it finds `01` -> `111` in the TLB (hit), puts the 3 frame bits in front of d, and gets the physical address. No page table access.
      - Cache terms: entry found in cache = **hit**, entry not found = **miss**.
      - This setup is called "paging hardware with TLB". Modern PCs normally have a TLB.

      **Paging hardware with TLB**

      ```
                logical
       CPU ---- address ---> [ p | d ]                        physical
                              |   |                           address
                              |   +---------------------> [ f | d ] ---> physical memory
                              |                              ^
                              +--> TLB                       |
                              |    page number | frame number|
                              |    ------------+------------ |
                              |         p      |     f  -----+ TLB hit
                              |                              |
                              +--> (TLB miss) page table     |
                                   index p ---> f -----------+
      ```

   6. **TLB hit, TLB contains the mapping for the requested logical address.**
   7. **Address space identifier (ASIDs)** is stored in each entry of TLB. ASID uniquely identifies each process and is used to **provide address space protection and allow to TLB to contain entries for several different processes.** When TLB attempts to resolve virtual page numbers, it ensures that the ASID for the currently executing process matches the ASID associated with virtual page. If it doesn't match, the attempt is treated as TLB miss.
      - Problem: each process has its own page table, and on a context switch the page table (PTBR) changes, but the TLB still holds the previous process's entries.
        - Example: TLB holds P0's entry page 10 -> frame 100. Context switch to P1. P1 also looks up page 10 and checks the TLB first (it is fast). It finds page 10 -> frame 100, but that entry belongs to P0. P1 would access P0's memory location. This is wrong.
      - Solution 1: **flush the TLB on every context switch** (delete all its entries, reset it).
        - Not feasible due to cost: context switches are very fast and very frequent (a process is scheduled, soon goes for I/O, the next one comes in, and so on). Flushing every time means the TLB never fills with enough entries, so the purpose of the cache is wasted. Resetting a hardware device also has its own cost each time.
      - Solution 2: **ASID** in each TLB entry (TLB columns: ASID/process | page number | frame number).
        - P0 runs and stores (P0, page 10, frame 100). P1 comes after the context switch and looks up page 10. The entry for page 10 exists, but its ASID is P0, not P1, so it is a TLB miss for P1.
        - P1 goes to its own page table, resolves the frame (say 45), and adds (P1, page 10, frame 45) to the TLB.
        - This gives memory (address space) protection and lets the TLB hold entries of several processes at once, with no flushing.
   - Interview points: paging is a very important interview topic.
     - Is the page table separate for each process? Yes, because each process's logical address space is mapped to different frames in physical memory.
     - Where is the page table stored? In main memory.
     - How is paging made fast? Using the TLB, a hardware support faster than memory.
     - Can the TLB have entries of different processes? Yes, handled using ASIDs.
     - Be ready to explain the bit-level translation (p, d -> f, d using the page table) and the paging hardware with TLB diagram.
